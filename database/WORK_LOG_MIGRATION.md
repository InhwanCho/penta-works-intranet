# 기존 Pentaservice DB 이관 시 업무일지 분류

2026-10-07 기능 변경 기준. GitHub에서 운영하는 기존 서비스의 데이터를 새 인트라넷으로 가져올 때 **이 문서를 먼저 읽고** `scripts/migrate-firestore.mjs`와 함께 적용한다. 코드만으로 운영 데이터가 이동되지는 않는다.

## 메뉴와 데이터 기준

- 병원·장비: 병원(Site), 설치 장비, 부품, 병원 전체 서비스 이력. 부품 관련 여부와 무관하게 병원 방문/점검/수리/콜/ACR 등은 여기에 남긴다.
- 각 부품의 부품 이력: `service_repair_components`로 연결된 해당 부품의 기록만 조회한다. 본문에 부품 이름이 있다고 자동 연결하지 않는다.
- 사무실 장비·부품 수리/시험은 별도 **수리 기록** 메뉴에 저장한다. [수리 기록 이관 지침](WORKSHOP_REPAIR_MIGRATION.md)을 함께 적용한다.
- 업무일지: 병원 서비스가 아닌 사내행사, 공구 정리, 일반 사내 업무. `work_logs`에 저장한다. `EVENT` 사내행사, `TOOLS` 공구·사내정리, `OFFICE` 사내업무, `OTHER` 기타.
- 독립된 서비스 기록 메뉴는 제거했다. `/repairs`는 병원·장비로 이동한다. 개별 서비스 기록 URL/API/테이블은 기존 링크와 병원 이력을 위해 유지한다. 업무일지로 이동한 기록의 기존 상세 링크는 업무일지로 연결된다. 새 서비스 기록은 병원 선택이 필수다.
- MREyes는 병원의 `mreyes_site_id`로 사이트·장비·부품·병원 서비스 이력을 조회한다. 업무일지는 MREyes에 전달하지 않는다.

## 적용 순서

1. 운영 DB와 업로드 디렉터리를 백업하고, 원본 Firestore JSON도 별도 보관한다. 운영 전환 중에는 원본/신규 쓰기를 멈춘다.
2. 기존 DB의 적용 이력을 확인하고 미적용 스키마 SQL을 순서대로 적용한다. 특히 `010_service_workflow.sql` 다음에 `011_work_logs.sql`, `012_workshop_repairs.sql`을 적용한다. 기존 볼륨은 Docker 초기화 SQL이 자동 재실행되지 않는다. 새 코드 배포보다 스키마 적용이 먼저다.
3. `scripts/migrate-firestore.mjs`로 원본 백업, 보고서, `migrate.sql`을 생성한다. 이 도구는 원본을 읽으며 생성 SQL을 DB에 자동 실행하지 않는다. 생성 SQL은 전체 원본(사진·PM·ACR·일정 포함)을 가져온 뒤 **같은 트랜잭션 안에서** `scripts/classify-work-logs.sql`을 실행한다.
4. 생성 SQL과 보고서의 `orphanLogs`, `unlinkedLogReview`를 검토하고 테스트 DB에 적용한다. 이미 가져온 데이터에는 `START TRANSACTION;` 이후 `scripts/classify-work-logs.sql`을 실행하고 확인 후 `COMMIT;`한다.
5. 자동 이동은 공백을 제거한 **정확한 제목**이 `환송회` 또는 `복스알정리`인 활성 기록에 한정한다. 제목은 `service_title` 우선, 없으면 `equipment_name`을 사용한다. 각각 EVENT/TOOLS로 분류한다. 부품 또는 활성 서비스 일정이 연결된 기록은 자동 이동하지 않는다. 병원 ID가 있다는 이유만으로 사내 행사 기록을 병원 서비스에 남기지는 않는다.
6. 나머지 사내 기록은 **관리자 → 업무일지 → 기존 서비스 기록 이동**에서 검색·분류·선택하여 옮긴다. 이 화면에서는 병원 연결이 있는 기록도 검토할 수 있다. `ETC`, 병원 미연결이라는 이유만으로 일괄 이동하지 않는다. 실제 병원 서비스인데 병원 ID가 없는 기록은 이동 화면의 ‘원본 기록 보기·병원 연결 수정’으로 상세를 열고 수정 화면에서 해당 병원을 선택한다.
7. 테스트 DB에서 확인한 후 운영에도 같은 스키마/이관 SQL/검토 절차를 적용한다.

## 보존과 재실행

`work_logs.source_repair_id`는 유일하며 원본 기록 ID를 보존한다. 이동 시 제목·본문·작업일·작성자·생성/수정일을 복사하고 원본 `repair_requests`는 soft delete한다. 원본의 상세 필드, 댓글, 상태 이력, 사진 및 기존 파일 연결은 그대로 보존하고 업무일지 상세에서 원본 사진/첨부를 조회한다. 원본은 휴지통 조회·자동 정리·복구·완전삭제 대상에서 제외된다. 파일은 새로 복제하거나 다운로드하지 않는다.

이관 도구를 다시 실행해도 기존 업무일지를 덮어쓰지 않으며, 원본이 다시 활성화되면 분류 SQL 마지막 단계가 다시 숨긴다. 업무일지에서 삭제한 항목도 재이관으로 되살리지 않는다. 원본의 이후 변경을 업무일지에 반영하려면 별도 비교·검토해야 한다.

## 검증 항목

- 원본 활성 기록 수 = 이동 후 활성 서비스 기록 수 + 해당 원본에서 이동한 업무일지 수. 삭제 기록은 별도 집계한다.
- `source_repair_id` 중복 없음, 이동 원본은 서비스 목록·병원 이력·MREyes 응답·서비스 휴지통에 나타나지 않음.
- ‘환송회’는 사내행사, ‘복스알 정리’는 공구·사내정리에 표시됨. 원본 날짜·작성자·내용·사진·첨부가 열리는지 확인.
- PM/ACR/수리/콜과 부품 관련 기록은 병원 이력에 유지됨. 연결 부품/일정이 있는 기록의 이동은 차단됨.
- 병원 미연결 서비스 기록은 전환 전에 검토하여 병원에 연결하거나 업무일지로 이동함. 미해결 기록을 조용히 삭제하지 않음.
- 병원 `mreyes_site_id` 매핑, 부품 연결, 사진 수와 실제 내용까지 확인.

## 롤백

스키마 변경은 MariaDB DDL 특성상 데이터 트랜잭션과 별개다. 테스트 단계에서는 데이터 이동 트랜잭션을 ROLLBACK한다. 운영 배포 후 문제가 있으면 쓰기를 중단하고 DB·업로드 백업과 이전 코드 버전을 함께 복원한다. 이동 원본의 deleted_at만 해제하면 중복이 생기므로 단독으로 복구하지 않는다.
