# 회계 스키마

`init/013_accounting.sql`은 2026-10-12 검토한 최소 회계 구조다. 기존 사용자, 병원, 첨부파일, 감사로그를 재사용한다. 새 테이블은 15개다.

| 테이블 | 역할 |
|---|---|
| accounting_bank_accounts | 회사 계좌와 이관 기준 잔액 |
| accounting_bank_transactions | 실제 입출금과 내부이체 연결 |
| accounting_cards | 법인카드와 담당자, 결제계좌 |
| accounting_card_transactions | 카드 승인·취소·매입 및 최신 원본 |
| accounting_counterparties | 병원, 업체, 개인, 금융기관 |
| accounting_categories | 계정과목과 자금·손익 분류 |
| accounting_agreements | 정기계약, 분할판매, 가수금·대출 약정 |
| accounting_projects | 제품·부품 구매와 판매의 원가 연결 |
| accounting_ledger_entries | 분류된 장부 행과 입출금 예정 |
| accounting_payment_allocations | 부분 수금·지급·현금·상계 연결 |
| accounting_budgets | 연간·월간 목표 |
| accounting_payroll_runs | 월별 급여 작성과 확정 |
| accounting_payroll_details | 개인별 급여 명세 |
| accounting_payroll_items | 기본급, 수당, 공제, 회사 부담금 |
| accounting_documents | 증빙의 발행 정보와 첨부파일 |

## 설계 변경

- 내부이체는 계좌 거래의 연결 ID로 묶는다. 여러 거래가 나뉘는 이체는 transfer_group_key로 묶고 그룹별 입출금액을 검증한다.
- 수동 업로드의 파일명·시각·최신 원본 JSON은 금융거래에 보관한다. 재업로드 전후 값은 기존 audit_logs의 old_value/new_value를 이용한다. 전용 배치 테이블을 두지 않는다.
- 한 장부의 분할 행은 entry_group_key로 묶고 line_no로 구분한다. 합계 행은 중복 저장하지 않는다. 하나의 증빙은 여러 분류 행에 연결할 수 있다. 1차 구조는 장부 행당 대표 증빙 하나, 증빙당 첨부파일 하나를 지원한다. 복수 파일은 증빙 행을 추가할 수 있지만 장부와 증빙의 다대다 연결이 필요해지면 연결 테이블을 확장한다.
- 예정은 PLANNED 행으로 작성하고 실적 확정 시 동일 행을 CONFIRMED로 바꾼다. 예정 금액을 별도 비용으로 다시 생성하지 않는다. 수금·지급은 여러 번 배분할 수 있다. 1차 구조는 분류 행당 현재 예정일 하나이며 여러 예정일은 그룹 안의 분할 행으로 표현한다.
- 직원 탈퇴나 이름 변경으로 과거 급여 명세가 변하지 않도록 employee_key/name을 보존한다. 미가입·퇴사 직원도 user_id 없이 기록할 수 있다. 급여 합계는 항목에서 계산하므로 별도 합계 필드와 불일치하지 않는다.
- 사용자 수정과 원본 재수집을 분리한다. 수집은 금융거래 원본 필드만 갱신하며 장부·분류·메모·지급 연결을 자동으로 덮어쓰지 않는다.

## 금액과 집계

금액은 DECIMAL(18,2), 식별자는 문자열이다. 기존 손익 시트의 천원 단위는 이관 시 원 단위로 변환한다. 통화가 다른 거래는 합산하지 않는다. 외화 환산은 별도 확정된 환율과 기준일이 필요하다.

- 은행 거래는 입금/출금 중 하나가 양수다. 잔액은 관측값으로 유지한다. 기초잔액 시각 이후의 입출금만 가산하여 과거 거래와 중복 계산하지 않는다.
- BC 취소는 승인금액 자체가 음수인 CANCELLATION 행이며 취소금액은 0이다. SIGN 코드를 다시 곱하지 않는다. 하나는 SNAPSHOT 행에서 승인금액과 음수 취소금액을 합산한다. source_event_key에는 상태·매입일 등 변하는 항목을 넣지 않는다. 카드번호 마스킹 충돌과 부분취소 키는 파서에서 확인한다.
- 장부 amount는 환입·취소에 음수를 허용한다. direction은 채권/채무 방향이다. 지급 배분액도 장부 방향에 맞춘 부호를 사용한다. 환불은 음수로 기록한다.
- 잔액은 CONFIRMED 장부금액에서 CONFIRMED 지급 배분을 차감한다. PLANNED는 예상 자금에만 포함하며 확정 손익에 넣지 않는다. VOID 배분과 장부는 제외한다.
- CARD_BILL과 PRINCIPAL은 DB CHECK로 손익 제외를 강제한다. 카드 원사용을 비용으로 인식하고 계좌의 카드청구 대금 출금은 지급으로 연결한다. 내부이체·원금 상환은 비용으로 다시 만들지 않는다.
- 급여 총지급액 = EARNING 합계, 공제액 = DEDUCTION 합계, 실지급액 = 총지급액 - 공제액. EMPLOYER_CONTRIBUTION은 실지급액에서 차감하지 않는다. 환급·정산 항목은 음수를 허용한다. 급여 비용 장부와 실지급·예수금 지급 장부의 손익 처리를 구분하여 급여를 중복 인식하지 않는다.
- 연간 목표는 fiscal_month=0, 월간은 1~12다. 연간 목표와 월간 목표 합을 다시 더하지 않는다. 같은 버전·기간·분류·통화의 목표는 중복 저장하지 않는다.
- 월별 엑셀에서 반복된 채권·채무는 같은 장부로 매핑한다. 과거 요약만 가져오는 경우 상세 이관 기간과 겹치지 않게 확정해야 한다. 손익 시트에 섞인 가수금·원금 상환을 신규 손익에 그대로 복사하지 않는다.

## API 구현 시 필수 검증

013은 DB 기반을 추가한다. 카드·계좌 원본 수집 API와 화면은 014와 함께 구현했다(`docs/ACCOUNTING_API.md` 참고). 장부·급여·지급 배분의 쓰기 API는 후속 구현이다. 아래의 교차 행 규칙은 CHECK 제약만으로 보장할 수 없으므로 해당 쓰기 API 구현 시 트랜잭션으로 적용해야 한다.

1. 지급 배분 저장은 원본 거래와 대상 장부를 일정한 ID 순서로 SELECT FOR UPDATE하여 잠근다. 금액·통화·방향, 거래별/장부별 누적 배분 한도, VOID 상태를 검증하고 감사로그와 함께 커밋한다. 상계는 양쪽 장부를 잠그고 서로 반대 방향이며 같은 통화인 경우에 한 번 기록한다. 잔액 조회 시 상계 대상 장부에도 같은 금액을 반영한다.
2. 내부이체는 자기 자신과 연결하지 않고 회사의 다른 계좌·동일 통화·입출금 반대 방향을 검증한다. 직접 연결은 상호 대칭으로 기록한다. 수수료는 별도 비용으로 배분한다. 이체 확인으로 기존 비용 장부가 남아 중복되는지 확인한다.
3. 급여 확정 시 모든 직원의 항목을 검증하고 확정 이후 항목 편집을 차단한다. 수정은 명시적 재개방·감사로그를 거친다. 월별 장부 생성에는 generation_key를 부여해 버튼 재실행으로 중복 생성되지 않게 한다.
4. 재수집 후 이미 지급 배분된 거래금액이 달라지면 재대사 대상으로 처리한다. 기존 배분을 조용히 변경하지 않는다. 취소 원거래는 같은 카드의 원승인인지 확인한다.
5. 장부 수정은 version에 의한 낙관적 잠금을 적용하고 audit_logs에 이전/이후 값을 기록한다. raw_payload와 감사로그에 API 인증키·비밀번호는 저장하지 않는다. 계좌번호는 외부 키로 암호화하고 식별값은 은행·계좌번호의 HMAC을 사용한다.
6. ACCOUNTING/ADMIN을 서버에서 검사한다. 급여 명세는 별도 급여 조회 권한을 구현하기 전 일반 회계 API에 노출하지 않는다. 증빙 다운로드도 장부 접근 권한을 확인하고 연결 시 기존 files의 TEMP 상태·만료를 처리한다.
7. 계정과목 부모의 순환 연결, 계약일 규칙(31일/휴일), 증빙 상태와 금액을 검증한다. 상이한 통화의 지급은 환산 설계 전 거절한다.

## 적용 및 확인

기존 운영 DB는 deploy/backup.sh로 백업한 뒤 013_accounting.sql을 적용한다. MariaDB DDL은 암묵적 커밋이 있으므로 전체 파일이 하나의 트랜잭션으로 롤백되지 않는다. 실패 시 오류를 먼저 해결하고 다시 실행한다. 새 테이블은 IF NOT EXISTS로 재실행 가능하며 완료 후에만 schema_migrations에 기록한다. 기존에 같은 이름의 다른 구조가 있으면 재실행 전에 구조를 비교해야 한다.

deploy/deploy.sh의 기존 마이그레이션 루프에 013을 추가했다. 마이그레이션은 테이블과 제약만 만들며 원본 금융 데이터·급여·목표를 넣지 않는다. 서비스 재시작 없이 SQL만 적용할 수 있다.

검증 도구 `scripts/test-accounting-schema.py`는 별도 MariaDB 서버의 임시 DB에서 실제 선행 스키마 001/002와 013 생성·재실행, 중복·금액·참조 제약, 부분 지급과 급여 합계를 검증한다. 운영 DB를 테스트 대상으로 사용하지 않는다.

기존 전체 초기화 경로에는 별도 문제가 있다. 현재 001에는 제조국·제조일·제조사 컬럼이 이미 없지만 003은 해당 컬럼을 다시 삭제하려 하여 빈 DB의 순차 초기화가 중단된다. 회계 검증에서는 필요한 선행 스키마만 적용하며, 이 결과를 전체 001~013 초기화 성공으로 해석하면 안 된다. 기존 운영 DB에 013을 추가하는 경로에는 해당 003을 재실행하지 않는다.
