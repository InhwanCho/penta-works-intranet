# 사무실 수리 기록 이관 지침 (2026-10-07)

기존 GitHub 서비스/인트라넷 DB를 가져올 때 [업무일지 이관 지침](WORK_LOG_MIGRATION.md)과 함께 읽는다.

## 세 가지 기록의 위치

- **병원·장비 → 병원 서비스 이력**: 병원 현장 방문, PM, ACR, 교체, 고장 수리, 콜. 부품에 관련되지 않은 기록도 포함한다.
- **수리 기록** (`workshop_repairs`): 사무실에서 장비·부품을 수리/시험한 기록. 병원 선택을 요구하지 않으며 여러 대의 개별 시험 결과를 저장한다.
- **업무일지** (`work_logs`): 사내행사, 공구 정리, 일반 사내 업무. 수리·테스트는 여기로 옮기지 않는다.

수리 상태는 RECEIVED 접수, IN_PROGRESS 수리 중, TEST_REQUIRED 테스트 필요, TEST_FAILED 테스트 실패, COMPLETED 수리 완료. 개별 장비·부품은 `workshop_repair_units`에 순번, S/N(알 때만), 상태, 오류 축, 테스트 결과를 저장한다. 2EA라도 한 대는 Y축, 다른 대는 Z축처럼 각각 관리한다. 하나라도 실패하면 전체 상태는 테스트 실패이며, 모두 완료된 경우에만 전체 수리 완료로 저장할 수 있다.

## 스키마와 이관 순서

1. DB/업로드/Firestore 원본을 백업한다. `011_work_logs.sql`에 이어 `012_workshop_repairs.sql`을 적용한 후 새 코드를 배포한다. 기존 Docker 볼륨에서는 스키마 SQL을 직접 적용해야 한다.
2. 기존 DB 자체를 가져오면 workshop 테이블 4개와 연결된 원본 repair_requests, 원본 service_photos/file_links/files도 함께 이관한다.
3. 새 DB로 재구성한다면 먼저 원본 서비스 기록·작성자·사진·첨부를 가져오고, 사무실 수리 기록을 분류한다. **삭제된 기록도 작성자와 실제 내용이 확인되고 사용자가 복원을 요청한 사무실 수리 기록이면 가져올 수 있다.** 삭제된 PM/병원 기록을 일괄 복원하지 않는다.
4. `scripts/seed-workshop-repairs-20261007.sql`은 확인한 운영 DB의 원본 2~7번(admin1/조인환 작성, hospital_id 없음)과 이번 요청 2건을 반영하는 재실행 가능한 SQL이다. **다른 DB에서는 숫자 ID만 보고 실행하지 말고 작성자·제목·작업일 대응을 확인한 뒤 source_repair_id를 맞춘다.** 이 6건은 새 인트라넷에서 직접 작성했으므로 Firestore 백업만 가져오면 누락된다. 원본 운영 DB 백업도 필요하다.
5. 추가 후보는 관리자 **수리 기록 → 기존 수리 기록 가져오기**에서 선택한다. 본인의 삭제된 원본도 표시된다. 병원 부품/서비스 일정에 연결된 기록은 연결 검토 전 이동이 차단된다. 업무일지로 이미 이동한 원본은 중복 이동할 수 없다.
6. 원본 DB 대신 Firestore 백업에서 누락된 사무실 사진을 복구할 때는 `node scripts/import-workshop-photos.mjs BACKUP_JSON OUTPUT_SQL`로 SQL을 생성한다. workshop의 외부 source 키와 대응되는 사진만 저장하며 실제 SQL 실행은 별도다. 사진 원본 blob·파일명·MIME·크기·원본 생성일을 보존한다.
7. Firestore 전체 이관 도구는 이미 workshop에 가져온 외부 source_system/source_id와 원본 서비스 ID를 연결한다. 병원 미연결이라는 이유만으로 모든 기록을 자동 수리 기록으로 분류하지 않는다.

## 원본과 사진 보존

workshop의 `source_repair_id`는 원본 ID를 유지하며 유일하다. **workshop으로 이동할 때 원본의 삭제 상태나 본문을 바꾸지 않는다.** 새 코드의 서비스 목록/검색/달력/병원 이력/MREyes 조회에서 workshop으로 연결된 원본을 제외한다. 따라서 배포 전의 기존 코드에서는 원본이 그대로 보이며, 배포 후에는 새 수리 기록으로 표시된다.

원본 사진·첨부는 그대로 유지하고 수리 기록 상세에서 연결해서 읽는다. 원본의 완전삭제/자동 휴지통 정리/서비스 수정은 새 코드에서 차단한다. 삭제했던 원본을 가져와도 원본은 삭제 상태 그대로이며 새 수리 기록이 활성화된다. 기존 서비스 상세 URL은 새 수리 기록으로 연결된다. 수리 기록 자체를 삭제해도 원본이 서비스 메뉴로 되살아나지는 않는다.

이관 SQL은 반복 실행해도 수리 기록/개별 항목을 중복 생성하지 않고, 나중에 사용자가 수정한 상태를 초기값으로 덮어쓰지 않는다. 원본만 다시 이관할 때는 전체 도구의 workshop 원본 연결 단계까지 실행해야 한다. 별도 증분 도구를 사용하면 외부 source 키로 source_repair_id를 먼저 맞춰 중복 서비스 표시를 방지한다.

## 확인

원본 6건과 수리 기록 6건의 본문·작성자·작업일·상태, 사진/첨부를 대조한다. VRE 개별 2개가 COMPLETED, Gradient 개별 2개가 TEST_FAILED이며 축이 Y/Z인지 확인한다. 동일 원본의 중복 생성 없음, 구형 수리 완료 기록 유지, 병원 서비스/MREyes에 사무실 수리 기록이 나타나지 않음, 수리 기록의 검색/상태 변경/삭제 권한도 확인한다.
